## G8 trust gap (accepted for the hackathon)

Anyone holding the `ShubhamU55` GitHub token can post a `pr-review` commit status directly (bypassing the actual review agents), which the branch-protection rule for `main` would then treat as a passing required check. This is a real gap: a compromised or careless use of that token can force-pass the security/code-review gate.

**Accepted for the hackathon** because the token is solo-owned and the alternative (a dedicated bot identity with narrower scopes) is out of scope for the submission deadline. **Mitigated by:**

- the owner's `hold` label, which blocks auto-merge regardless of check status (§8.9);
- the pre-submission full security pass by `security-reviewer` on Opus over the whole repo (§8.10), which would catch a forged status before 30 Oct.

This gap is **not** mitigated by any automated test; it is a documented, owner-accepted residual risk.

A second, narrower trust gap of the same shape: an agent that redefines `git`/`cat` as a shell function or alias inside its own Bash command (e.g. `cat() { printf …; }; git commit -m "$(cat <<'EOF'...)"`) can make the real command/heredoc content diverge from what `pre-bash-commit-quality.cjs` reads back, forging a commit message past it. **Accepted, not fixed** — an agent willing to redefine core utilities to lie to its own tooling has materially more direct ways to misbehave that no `PreToolUse` command-text hook can catch; the same mitigations above (owner `hold` label, pre-submission Opus security pass) are the backstop.

## Out of scope for this model

Real bureau integrations (F5: no public CIBIL API; a licensed partner is Future work), anything beyond the demo provider's sample PANs, and infrastructure outside Supabase/Vercel/EAS hosting.
