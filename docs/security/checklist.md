# Security checklist

Derived from `docs/security/threat-model.md` and PRD/CLAUDE.md product rules (spec §8.10). One checkbox per rule. Each names the plan whose test enforces it; "today" means it is already enforced in this repo, not deferred to a future plan. `.claude/agents/security-reviewer.md` checks this list on every security-triggering change and before submission.

## PAN, consent and demo

- [ ] PAN is never stored in full (hash + last 4 only). **Enforced by: Plan 3** (Supabase schema/migration test).
- [ ] PAN is never logged in full, anywhere (app, admin, Edge Function logs). **Enforced by: Plan 3** (a test greps log statements for PAN patterns).
- [ ] PAN is masked everywhere in the UI (`ABXXXXX34F`). **Enforced by: Plan 4b** (mobile screen test/E2E).
- [ ] Consent to fetch a credit report is recorded with a timestamp. **Enforced by: Plan 3** (schema) and **Plan 4b** (consent screen records it).
- [ ] The demo path ("Try sample profile", on-screen OTP) never touches a real bureau or sends a real SMS. **Enforced by: Plan 4b** (demo-path E2E, Maestro).

## RLS and data access (database-reviewer-derived)

- [ ] RLS is enabled on **every** table, deny-by-default. **Enforced by: Plan 3** (the RLS-on-every-table test, per §8.10).
- [ ] RLS policies use the `(SELECT auth.uid())` pattern, not a per-row function call. **Enforced by: Plan 3** (`database-reviewer` checklist, adapted from ECC's `agents/database-reviewer.md`).
- [ ] RLS policy columns are indexed. **Enforced by: Plan 3** (`database-reviewer` checklist).
- [ ] No `GRANT ALL` to application users; public schema permissions revoked. **Enforced by: Plan 3** (`database-reviewer` checklist).
- [ ] Foreign keys are indexed. **Enforced by: Plan 3** (`database-reviewer` checklist).

## Secrets

- [ ] Only the Supabase **anon** key ships in any client bundle (mobile or admin); the **service role** key lives only in Edge Function secrets. **Enforced by: Plan 3** (Edge Function review) and today's CI gate G4 (gitleaks secret scan on every PR).
- [ ] The Anthropic API key lives only in Supabase Edge Function secrets, never in the repo or a client bundle. **Partially enforced today**: the `protect-env` hook blocks agent writes to `.env*` and `config-protection.cjs` blocks agent writes to `.claude/settings.json`'s deny-list — but both only match the `Write|Edit|MultiEdit` tools, not a Bash-tool edit (`sed -i`, `cat > file`, a shell redirect). `.claude/settings.json` separately denies reads of `.env*` and SSH/AWS credential paths; CI gate G4 (gitleaks) is the backstop that does cover the Bash-tool path.
- [ ] `.claude/**` carries no hidden Unicode (zero-width/bidi/BOM) or hidden `<!--` instructions that could steer an agent into leaking a secret. **Enforced today**: `.claude/hooks/tests/config-audit.test.mjs`.
- [ ] Agents cannot bypass git hooks (`--no-verify`, `core.hooksPath` redirection) to skip the checks above. **Enforced today**: `block-no-verify.cjs` (this task, W1-4) is a `Bash`-matched PreToolUse hook — it inspects the command Claude is about to run and blocks it before it executes. **Not enforced by an actual git hook**: no `commit-msg`/`pre-commit` git hook is installed in `.git/hooks`, and `core.hooksPath` is untouched; this is policy enforced at the tool-call layer, not at the git layer, so it only covers commands run through this harness's Bash tool.
- [ ] Agents cannot weaken a lint/format config, `.claude/settings.json`, `.claude/settings.local.json`, or this repo's own guard-hook scripts, to make a check pass instead of fixing the problem. **Partially enforced today**: `config-protection.cjs` (this task, W1-4; extended in fix round 1) blocks `Write|Edit|MultiEdit` on exactly: known lint/format config basenames and patterns (ESLint/Prettier/Stylelint/Biome/Ruff/markdownlint); `.claude/settings.json` and `.claude/settings.local.json` (the latter blocked unconditionally, including first-time creation); and five named guard scripts — `block-no-verify.cjs`, `pre-bash-commit-quality.cjs`, `config-protection.cjs`, `protect-env.mjs`, `lib/shell-scan.cjs`. **Nothing more**: `.claude/hooks/lib/contracts.mjs` and the rest of `.claude/hooks/**` stay editable (W2–W4 need to edit them), and a Bash-tool edit (e.g. `sed -i` on any of the above) is not caught by this hook at all — CI gate G1 (lint) and a human/`pr-reviewer` diff review are the backstop for that path.

## Commit message integrity

- [ ] A commit message that fails our conventional-commit format, carries `Co-Authored-By`/"Generated with" attribution (including via `--trailer`, colon or `=` form), uses `--amend`, reads its message from an unreadable or unrecognized source (`-F`/`--file`/`-t`/`--template`/`-e`/`--edit`/`-c`/`--reedit-message`/`-C`/`--reuse-message`/`--fixup`/`--squash`, an unquoted heredoc delimiter, a bare `$(...)`, ANSI-C `$'...'` quoting, a forged nested heredoc, or any other unrecognized `-`/`--` option), or has no message flag at all, is BLOCKED (exit 2), not warned. **Enforced today**: `pre-bash-commit-quality.cjs` (PreToolUse, `Bash` matcher). Fix round 1 replaced a substring check (`command.includes('git commit')`) with real parsing via the vendored shell scanner (`lib/shell-scan.cjs`), so `git -c k=v commit`, a double-spaced `git  commit`, a command chained with `&&`, or an environment-variable prefix no longer bypass it, and a non-git command that merely quotes "git commit" (e.g. a `grep`) no longer false-triggers it. A second review pass then found and closed: an unrecognized flag (e.g. `--mess`) being silently ignored whenever any other `-m` was present; `-Fm` being misread as a message flag instead of `-F`'s value; `--fixup=`/`-e`/`-c`/`-C` sourcing the message from somewhere this hook can't see; a `--trailer` `=`-form or dynamic-value attribution bypass; ANSI-C `$'...'` quoting read as a literal one-line subject when bash would actually expand it to a multi-line message; and a forged nested heredoc whose lazy-matched "body" could be made to include real shell source. The flag walk is now an **allowlist**, not a denylist: any `-`/`--` option after `commit` that isn't a recognized message flag, a known-forbidden message source, `--amend`, `--trailer`, or on a short explicit safe list, blocks as `commit-unknown-option`. **Not yet enforced elsewhere, or not covered by this hook at all**: there is no git-layer `commit-msg` hook (same caveat as the row above); the gate-checker drift guard's `checkCommitMessage` (`.claude/hooks/lib/contracts.mjs`) checks the same rule but only exists from **Plan 1c Wave 2 (W2-1)** onward, and only for commits made through a `/build`-style workflow task — not every commit a human or an ad hoc agent session makes. A CI-side lint of PR commit messages (independent of this hook) is **planned for W5-1**, not present today. **Fix round 2** (a scoped Opus re-review of fix round 1, two passes) closed N5 (a short-flag cluster's attached value, e.g. `-am'…'`/a whole-word-quoted `'-mstyle: bad'`, being validated against the wrong next word instead of the attached text), N6 (an NTFS alternate-data-stream or 8.3 short-name alias of a protected guard-hook path, in `config-protection.cjs`), and N7 (reworded this file's own prior overclaim). Its own attempt at closing N1 (unquoted-value bypasses) and N2 (wrapped/`bash -c` commits) kept finding new bypasses of the SAME shape — closing one denylisted expansion/wrapper form opened another: round 2's own `bash -c` recursion, meant to make a `$VAR`-carrying script argument "fail closed", actually read an outer-shell `$VAR`/`$(...)` expansion landing inside the inner script's quotes as literal, and so failed OPEN on an attributed message. **Fix round 3** replaced that whole denylist approach: every commit segment is now allowlisted by LITERALNESS (`isLiteralWord`/`isFullyQuotedLiteral`), not denylisted by shape. Current behavior: a message/trailer value, a `-c`/`--config-env` setting, a leading `VAR=value` assignment, and every OTHER word in the segment (bare positional words included) must be fully literal — not `word.dynamic` (the vendored scanner's own `$(...)`/backtick/bare-`$VAR` tracking), and carrying no UNQUOTED brace/glob/tilde character; a double-quoted value is unaffected by brace/glob/tilde (bash doesn't expand those inside `"..."` either — round 2 had wrongly over-blocked ordinary subjects like `-m "fix: why does it fail?"` on this point, now corrected). A commit wrapped in `env`/`command`/`time`/`!`/an `if`/`while`/`until`/`do`-style compound keyword (including the wrapper taking its own options, e.g. `env -i`/`command -p`/`time -p`) or a `$(...)` command substitution is still found. A `bash`/`sh`/`dash`/`zsh`/`ksh` `-c`-family argument is recursed into ONLY when its own option parsing unambiguously finds a SINGLE, fully literal script word; an unmodeled option shape (`-o pipefail`, a bare `--`, a quoted `"-c"`), no `-c` at all (a script file, or the shell fed via stdin/a heredoc/a pipe instead), or a dynamic/brace-expanded script argument instead BLOCKS outright whenever the command's own text mentions "commit" anywhere, rather than silently passing or being fooled by what the argument looks like after substitution. The same block-if-mentions-commit rule (not full unwrapping) now also covers `sudo`/`exec`/`eval`/`nohup`/`nice`/`timeout`/`xargs`, `env -S` (which re-tokenizes its own payload rather than running it directly, so is not treated as a transparent wrapper the way plain `env` is), and a dynamic command word (`$(echo git) commit …`). A `-c`/`--config-env` setting is blocked when its key matches a sensitive namespace (`trailer.*`/`include.*`/`includeIf.*`/`alias.*`, generalizing N3 past `trailer.*.key` alone) OR its key/value is not literal. A `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`/`PARAMETERS` environment variable anywhere in the command text — bare, via `env`, or via an earlier `export` — is blocked the same belt-and-braces way. A QUOTED `VAR="a b"` assignment prefix is now correctly detected too (a real regression vs. the original 702cb8f substring check, not new hardening: the old `!word.quoted` guard wrongly stopped unwrapping at the first quoted prefix); only a DYNAMIC assignment value blocks. **Residual gaps, still not fixed (not an exhaustive list), per fix round 3's binding ruling:** `git merge -m`, `git commit-tree`, `git revert`, `git cherry-pick` and `git pull` (with a merge) can all create a commit with a message, and none of them are recognized as a `commit` subcommand by this hook. A repo-configured git alias (`git -c alias.x=commit x -m …`) is invisible to it, as is a trailer-key (or any other) alias set via a PERSISTED `git config`/`.gitconfig` entry from an earlier command rather than visible in this command's own text. An agent that redefines `git`/`cat` as a shell function or alias inside its own command can forge what this hook reads back (accepted residual — see `docs/security/threat-model.md`'s "G8 trust gap" section). **Backstop for this whole class**: the W2-1 drift guard's post-expansion check of the stored commit's actual `%B` body (it sees what git actually wrote, not the command text), the W5-1 CI commit-message lint, and G8's existing mitigations (owner `hold` label, pre-submission Opus security pass). Finally, this hook imports its pass/fail rules from `.claude/hooks/lib/contracts.mjs`, which is deliberately left editable for Plan 1c Waves 2–4 (`config-protection.cjs` does not protect it) — an edit there could silently weaken what counts as a violation; PR review is the backstop for that, not a hook.

## Mobile (MASVS / OWASP Mobile Top 10)

- [ ] Session tokens use `expo-secure-store`, never plain `AsyncStorage`. **Enforced by: Plan 4b**.
- [ ] No HTTP (plaintext) network calls; only HTTPS to Supabase/Edge Functions. **Enforced by: Plan 4b**.
- [ ] No debug logs in release builds. **Enforced by: Plan 4b** (release build check, per §8.10).
- [ ] The release APK has no hardcoded secrets or debug backdoors (MASTG-STORAGE / MASTG-CODE checks). **Enforced by: Plan 4b**.

## LLM Edge Function

- [ ] The function treats all input as untrusted; it never executes or reflects instructions found in that input as if they were from the owner. **Enforced by: Plan 3** (Edge Function tests; `wrapUntrusted` pattern from `contracts.mjs` is the model for fencing).
- [ ] The function only words numbers the rules engine already computed; it never computes or invents an amount, date or score (CLAUDE.md non-negotiable 2). **Enforced by: Plan 3**.
- [ ] A template fallback exists so the app works if the LLM call fails. **Enforced by: Plan 3**.
- [ ] The function has a timeout and rate limiting. **Enforced by: Plan 3**.
- [ ] A predicted score is never shown exact; always a 300–900-clamped range plus reasons, labelled as an estimate. **Enforced by: Plan 2** (predictor engine test) and **Plan 4b** (UI copy).

## Admin

- [ ] Admin routes/RPCs require an admin-role claim, checked server-side (never only hidden in the client UI). **Enforced by: Plan 5**.
- [ ] Rule changes and sample-profile edits are recorded in the audit log (who/when). **Enforced by: Plan 5**.

## Agent-config security and the G8 trust gap

- [ ] A `pr-review` commit status can only be posted by the `pr-reviewer` workflow, not forged by prompt injection from an untrusted diff. **Partially enforced today** (`wrapUntrusted` neutralizes forged BEGIN/END fence markers in `contracts.mjs`); the residual risk is the G8 trust gap below, which has no automated test.
- [ ] **G8 trust gap is documented and owner-accepted** (see `docs/security/threat-model.md`): anyone holding the `ShubhamU55` token can post a passing `pr-review` status directly. Mitigated by the owner's `hold` label and the pre-submission security pass, not by a test.
