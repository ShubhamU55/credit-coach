## Rulings

- Ruling: persona data lives in the third migration (`default_sample_profiles()`), and `seed.sql` only calls `reset_demo_data()` - `supabase db push` does not run `seed.sql`, and the hosted project needs the personas for the demo; one source also means `reset_demo_data()` and the seed cannot drift - cost if wrong: a persona edit is a new migration, not a seed edit.
- Ruling: Aarav comes from docs/design.md section 8 exactly; Ishita (thin file) and Rohan (recovering) use the INFORMATION_ARCHITECTURE edge-state personas (PAN, score, Kotak 811 overdue minimum 1,450, ICICI Amazon Pay minimum 2,880, cash 3,000, one FD-backed card, 14 months). Numbers the docs do not give (limits, outstanding, statement days, Ishita's cash 15,000) are mine; a vitest case confirms the documented shortfall (Rohan: ICICI funded 1,550 of 2,880, short 1,330) holds with them - cost if wrong: the owner edits the JSON block in a new migration; PD-9 screens that hard-code other numbers would disagree.
- Ruling: the PRD recovering persona says "one missed payment 4 months ago, 2 cards + 1 personal loan, 2 hard inquiries, score ~650"; the IA file says Kotak is overdue now. I used both (`missed_payments = 1` plus an overdue Kotak minimum) - cost if wrong: none for the plan; the predictor's missed-payment input may be double-counted by PD-2 wiring.
- Ruling: admin = `app_metadata.role = 'admin'` on a non-anonymous user (`public.is_admin()`), not a roles table - `app_metadata` is writable only by the service role, so a user cannot grant it to themselves; a table would need its own RLS and a bootstrap row - cost if wrong: a role change needs a token refresh.
- Ruling: admins can read `profiles`, `cards` and the masked overview, but never `payments` or `consents` - the PRD's Users page needs only masked identity and card counts - cost if wrong: add a select policy.
- Ruling: `reset_demo_data()` callable by admin, `service_role`, or a direct session with no JWT role claim (migrations, SQL editor, pg_cron); `anon` has EXECUTE revoked, `authenticated` non-admins get 42501. A first draft checked `session_user in ('postgres', ...)`, which the embedded run showed lets every caller through (the harness logs in as postgres and uses SET ROLE; on hosted Supabase it would be authenticator, so production was probably fine, but the check depended on how the connection was opened) - cost if wrong: n/a, fixed.
- Ruling: `explain` returns 200 with the template for every failure after the input is accepted, and 400/405/413 only for bad requests - matches the app contract (anything non-2xx or odd also falls back there) and keeps the app label honest (`source: "template"`).
- Ruling: grounding is by number set, same token rule as the app (digits with commas and decimals; commas, currency, ordinal suffixes ignored), over the payload's values only (not keys, so `aimFor10` does not legalise "10"); numerals inside card names and ISO dates count as present. The prompt also passes the engine template as REFERENCE TEXT so the model copies exact formatted figures - cost if wrong: a stricter check than the app's costs only extra template answers.
- Ruling: template copy instead of a cross-package import - an Edge Function deploy bundles only `supabase/functions/`, and Deno needs `.ts` suffixes the engine does not use. The copy is `functions/explain/template.ts` (about 90 lines); `template.test.ts` pins it equal to `buildTemplateExplanation` for the Aarav plan, the 10% switch, a 20% threshold, Rohan, Ishita, zero cash, and 150 random persona/cash/threshold/switch combinations (fast-check) - cost if wrong: if the engine wording changes, that test fails until the copy is updated (intended).
- Ruling: card names in the payload must match a strict character set (letters, marks, digits, space and `.&'()/+-`, 60 chars) - they are user-typed and go into a prompt; `\n`, quotes, backticks and angle brackets are rejected with 400 - cost if wrong: a legitimately odd card name gets the app's local template.
- Ruling: new workspace `supabase` with devDependencies already present in the repo (`vitest`, `fast-check`, `@types/node`, the engine as `workspace:*`) - no new package versions, only a lockfile entry for the workspace; the ticket owns `supabase/**` but `pnpm-workspace.yaml` and `pnpm-lock.yaml` are shared hotspots (two small additive edits). On a lockfile conflict: `git checkout origin/main -- pnpm-lock.yaml && pnpm install`.
- Ruling: no pg_cron daily reset migration (PRD section 6 asks for 2 to 5 Nov) - it needs the hosted extension; the exact SQL is in OWNER-STEPS section 7.

What changed:

- **A. Who may call `explain`.** New `auth.ts`: the bearer token must be a JWT with role `authenticated` and a uuid `sub` (the bare anon key, role `anon`, is turned away without a network call), then Supabase Auth `/auth/v1/user` must confirm the same id (anonymous sign-in users pass). 401 unauthenticated, 503 when Auth is unreachable, 600 ms budget. New `ratelimit.ts`: fixed window, in memory, 10 per minute per user and 30 per minute per address (`x-forwarded-for`), checked before the body is read; the 11th call gets 429 with `Retry-After` and the model is not called. Documented as best effort; the durable Postgres counter is described in OWNER-STEPS. OWNER-STEPS no longer suggests `--no-verify-jwt` anywhere (a test pins that), and now has the Anthropic spend cap and the anonymous-sign-in CAPTCHA steps (with the demo-path trade-off).
- **B. Consents.** `granted_at` and `id` are overwritten by a BEFORE INSERT trigger (test: a 2020 value and a chosen id are replaced). Ruling: instead of RESTRICT (which would make deleting an account impossible, because profiles cascade from auth.users) I dropped the foreign key on `consents.user_id`: a consent row survives both a profile delete by the user and an auth user delete (tested for both). Cost if wrong: orphan consent rows need an owner cleanup with the service role; RLS still shows a row only to the matching user id. `reset_demo_data()` and `adopt_sample_profile()` never delete profiles, so they are unaffected.
- **C. Grounding.** New `grounding.ts` replaces `ground.ts`. Numbers are classified: money must be an amount of the card named in the same sentence (or cash used or left over), a percent must be a utilization or the threshold, a date must be a (day, month) pair from the payload, an ordinal must be a payload day, a bare number must be an amount or a step; digits inside card names are part of the name. Date digits no longer legitimise percents or amounts. Wording denylist: score claims (will, could, reach, hit, jump and similar, either order), closing or cancelling a card, guarantee, spelled-out numbers (one to ninety, hundred, thousand, lakh, crore and more), URLs and markdown links and markup. Card names are removed before the wording check, so a card called "One Card" is fine. `stop_reason` must be `end_turn` or `stop_sequence` (refusal, tool_use, pause_turn, max_tokens and missing all fall back). The prompt now says to write numbers as digits. **Known limit:** two amounts swapped between two cards named in the same sentence are not caught (template-style lists name several cards); the cost is a wrong-but-grounded sentence.
- **Mobile (PD-11 merged code, minimal).** `apps/mobile/src/explain/grounding.ts` is a byte-identical copy (parity test in the supabase workspace compares the files; the file has no imports). `client.ts` now calls it, drops the "numbers from the template are allowed" rule (that test was reversed), and takes an optional `ExplainConfig.accessToken` used as the bearer token (the anon key stays in `apikey`). **A mobile PR rebuild and evidence run is required because `apps/mobile` changed.** The app integration must pass the session token from supabase-js (PD-4/PD-9 wiring, not done here); without it the function answers 401 and the app shows its template.
- **D. Timeouts.** `MODEL_TIMEOUT_MS` is 2000 (was 3000). A test reads `EXPLAIN_TIMEOUT_MS` from the app client source and asserts model time at most that minus 750 ms and user lookup plus model at most that minus 250 ms (2600 of 3000). The app's 1500-char limit is also pinned.
- **E. RLS tests.** 204 checks. The audit log now holds a row before the "cannot read" checks; B writes against A; A repointing a card or payment at B; anon INSERT, UPDATE, DELETE, TRUNCATE on every user table and on sample_profiles, coach_rules, audit_log; non-admin INSERT and DELETE on coach_rules and INSERT on audit_log; TRUNCATE by authenticated and by the admin; the admin updating or deleting others' cards, profiles and payments touches 0 rows (counted with a helper, not assumed); exact counts replace the loose ">= 3".
- **F.** PAN-shaped CHECK on the free-text columns (any case); the admin no longer reads card rows (the overview counts through a SECURITY DEFINER helper; README updated, PD-14 needs counts only); `valid_sample_report` CHECK plus defaults in `adopt_sample_profile` so an admin edit cannot break Try sample profile (tested: missing limit, text limit, day 32, PAN-shaped name rejected; a minimal report adopts with zero defaults); `expectTypeOf` parity between the engine and server payload types (checked by `tsc`); a null-utilization parity case; tests for HEAD, DELETE, PATCH (405), text/plain and a missing content type (415, a behaviour change: the function now pins application/json), an own `__proto__` key, 1e999 and a utilization of 1001.

Rulings.** SBI has no due date this cycle (design.md section 8) but `cards.due_day` is NOT NULL, so the persona keeps dueDay 14 as a placeholder: the app and engine must key "no due date" off `minimum_due = 0` and `last_statement_balance = 0`, never off `due_day`.
