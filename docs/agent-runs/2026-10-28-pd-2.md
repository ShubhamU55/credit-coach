### Model, in one paragraph

Each of the seven PRD §5.5 factors maps to a subscore in 0–1 through a monotone piecewise-linear
curve. The model score is `300 + 600 × Σwᵢsᵢ/Σwᵢ`.

- **With an anchor:** the centre is `anchor + 0.25 × (model − anchor)`. The real bureau score
  dominates and the rules nudge it. The half-width is `round(10 + 0.2 × daysSinceAnchor)`, capped
  at 60. That gives 20 points wide on the anchor day, 28 at Aarav's 19 days and 120 at most. The
  window slides inside 300–900 instead of clipping, so `low < high` always holds.
- **Without an anchor:** the 50-point band the model lands in (e.g. "Good: 700–749"), with
  `isRoughBand: true`.
- **Reasons:** the top 3 factors by weighted gap against a typical-borrower reference profile.
  Each carries up, down or flat plus its own numbers (e.g. `{ pct: 81 }`).
- **No exact score anywhere:** there is no `score`, `center` or point field in any output, and a
  test walks every key to check this.

## Calibration statement

**The default weights and curves were calibrated to the Aarav demo fixture** (docs/design.md §8).
They are not derived from CIBIL's model, which is proprietary (F6). A throwaway scratch script swept
weights and curve points until all three fixture ranges came out exactly:

| Aarav state                                                 | Required     | Engine       |
| ----------------------------------------------------------- | ------------ | ------------ |
| Now (anchor 724 on 2 Oct, today 21 Oct, util 45% / max 81%) | 708–736 Good | 708–736 Good |
| Follow plan, 10% switch off (15.3% / 30%)                   | 724–752      | 724–752      |
| Follow plan, 10% switch on (7.3% / 10%)                     | 731–759      | 731–759      |

Default weights: payment history 35, overall utilization 11, max-card utilization 11, hard
inquiries 12, credit age 16, open accounts 7, credit mix 8 (total 100).

## Rulings

- **Ruling: the anchor blend uses `modelShare` 0.25.**
  - Why: the bureau's real score stays dominant, and one share parameter makes the calibration
    reproducible.
  - Cost if wrong: one config number. The fixture ranges would need recalibrating.
- **Ruling: the zones are the design mockup's (Poor < 550 ≤ Fair < 650 ≤ Good < 750 ≤ Excellent),
  marked as placeholders in config.** The rough band is a 50-point bucket labelled with its zone.
  - Why: design.md §6.13 draws these zones. PRD/IA's "Good: 700–749" example is a 50-point bucket,
    and this ruling satisfies both.
  - Cost if wrong: config edits only.
- **Ruling: closing a card keeps total outstanding (the balance is still owed), drops the limit,
  and never improves max-card utilization.**
  - Why: IA M12 says "with the same balances, utilization goes from 45.0% to 67.5%". Removing the
    balance would make closing the oldest card look positive, which is an anti-goal.
  - Cost if wrong: PD-10 shows a slightly different utilization.
- **Ruling: close-card always returns both a `limit-loss` and a `credit-age` warning.**
  `isOldestAccount: true` marks the oldest-card case.
  - Why: CLAUDE.md non-negotiable 4 ("never advise closing a card without warning about credit age
    and limit loss") outranks IA F4's "no age warning" for a non-oldest card.
  - Cost if wrong: PD-10 can hide the non-oldest age line. The data is there either way.
- **Ruling: close HDFC gives 698–726, not IA F4's 676–712.**
  - Why: 676–712 is an IA mockup value, not a PD-2 acceptance item. It is also 36 wide, while
    every other fixture range is 28. Hitting it would mean distorting the age and limit curves
    away from the calibrated Aarav ranges.
  - Cost if wrong: PD-10's close-card copy must use the engine's range, not the mockup's.
- **Ruling: "apply" is modelled as its hard inquiry only, because approval and the new limit are
  unknown.** "FD-backed card" adds a secured card with a limit of 90% of the FD at 0% use, plus a
  hard inquiry by default. Both are configurable (`fdLimitRatio`, `fdCardAddsHardInquiry`).
  - Why: F1 says applications are hard inquiries. Modelling a new limit would let "apply" raise the
    estimate.
  - Cost if wrong: config flags.
- **Ruling: the guard's impact range is the model's central drop × [1, 3], floored so that
  `pointsLow < pointsHigh`.**
  - Why: the real penalty is uncertain and skewed. Aarav gives 4–12 points.
  - Cost if wrong: the IA copy says "10–25" and "5–15". PD-10 must print the engine's numbers,
    not the mockup's.
- **Ruling: `follow-plan` takes the plan's payments as `{ cardId, amount }[]`. It doesn't add
  on-time payments.**
  - Why: the plan is PD-1's output, and PD-10's adapter maps it. Fixture calibration then rests on
    utilization alone.
  - Cost if wrong: a small upward shift if on-time months are added later.
- **Ruling: input errors split by kind.**
  - Non-finite numbers and malformed dates throw `RangeError`, matching `format.ts`.
  - Negative counts are floored at 0.
  - An unknown card or an invalid amount in a what-if returns `{ ok: false }` (standards: expected
    domain outcomes don't throw).
  - Cost if wrong: small, local changes.
- **Ruling: `predictor.ts` has its own small ISO-date parser.**
  - Why: `format.ts`'s `parseIsoDate` isn't exported, and `format.ts` isn't owned by PD-2.
  - Follow-up: dedupe into a shared date helper (PD-1's `reporting.ts` may provide one).
- **Ruling: the tests assume SBI is 38 months old and Axis 20.**
  - Why: the fixture gives only HDFC's age (6 yrs 2 mo).
  - Cost if wrong: PD-4's seed sets real ages. Only the test's "next oldest" number changes.

## Fix round 1 (coordinator review)

Commit `042d272` (`fix(engine): validate predictor config and reject unsafe what-if input`). Each
fix was test-first: the new tests went RED (missing export or wrong behaviour), then GREEN.

1. **Whole-config validation.** `validatePredictorConfig` in `predictor-config.ts` runs at the top
   of `predictScore`, `compareReasons` and `estimateShift`. It throws a `RangeError` that names
   the field. The rules:
   - `range.baseHalfWidth` is finite and at least 1.
   - `range.widenPerDay` is finite and at least 0.
   - `range.maxHalfWidth` is finite and at least `baseHalfWidth`.
   - `roughBandWidth` is a whole number in 2..600.
   - `modelShare` is in (0, 1].
   - `missedPaymentPenalty`, `noHistoryPaymentSubscore`, `olderInquiryFactor` and
     `creditMixSubscores.*` are finite and in 0..1.
   - Every curve is non-empty with finite points, strictly increasing inputs and subscores in
     0..1. Utilization and inquiry curves must be non-increasing; age and account curves
     non-decreasing. This is checked at runtime, so injected curves are covered too.
   - `zones` is non-empty with finite minimums.

   `predictScore` also asserts integer `low < high` inside 300–900 before returning, as a last
   guard. Every repro is now a `RangeError`: zero half-width (was 734-734), −5 half-width (was
   low > high), `modelShare` NaN, `roughBandWidth` 0 and 1, and `widenPerDay` −0.2. In the guard,
   `impactSpread.high` must keep `high × 600` finite, so 1e308 is now rejected. The new test file
   is `predictor-config.test.ts`: 31 bad configs, each checked both through the validator and
   through `predictScore`, plus the narrowest valid settings.
2. **Stronger monotonicity tests.**
   - A deterministic point-to-point test checks every default curve: the utilization and inquiry
     curves never rise, and the age and account curves never fall.
   - A new fast-check property runs the utilization check with `modelShare: 1` on anchored inputs
     (500 runs).
   - **Mutation proof:** a 0.68-at-40% point was inserted after 0.6 at 30% in the utilization
     curve. The deterministic tests (overall and max card) failed, along with "accepts the
     documented defaults" and the new property (22 failures in all, since validation rejects the
     default config everywhere). With the runtime monotone check also disabled, both utilization
     properties still failed on their own. The mutation was then reverted, and `cmp` against a
     backup confirmed the file is byte-identical.
   - **Root cause the mutation exposed:** the first version of the new property *passed* under
     the mutation. `fc.double` draws uniformly over IEEE-754 bit patterns, so almost every value
     sat near 0 and the 30–40% stretch was barely sampled. The round-0 mutation at 0% was caught
     only because it sat where the draws cluster. Utilization and step generators are now uniform
     tenths (`fc.integer(...).map(n => n / 10)`).
3. **Duplicate card ids.** `runWhatIf` returns `{ ok: false, error: 'duplicate-card-id' }` before
   applying any scenario. The test covers pay-card, follow-plan and close-card.
4. **`estimateShift` is internal.** It is removed from `index.ts`, and `guard.ts` imports it from
   `./predictor`. A test asserts it is absent from the public surface.
5. **Future anchors.** An anchor dated more than 1 day after `today` throws a `RangeError` that
   names `anchor.date`. One day is tolerated for time-zone skew. The property generator now stays
   within that tolerance.
