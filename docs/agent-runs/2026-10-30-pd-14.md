# PD-14 thin admin control center

## What was built (apps/admin only)

- **Login** (`/login`): Supabase Auth email and password through supabase-js on the server. The access token is kept in an httpOnly, sameSite=lax cookie (`secure` in production) for its lifetime. A `proxy.ts` does the optimistic redirect; the real check is `auth.getUser(token)` in the layout and in every server action. No self sign-up.
- **Non-admin**: the admin flag is `app_metadata.role === 'admin'` on a non-anonymous user, read from GoTrue's `/user` (never from `user_metadata`, never decoded locally). A non-admin sees "Not an admin" in place of every page and the save action refuses them before any database call.
- **Rules** (`/rules`): a form for every editable `coach_rules` field. One pure `validateRules` (`src/lib/validation.ts`) mirrors the CHECK ranges exactly and runs in the browser before submit and in the server action before the UPDATE. The UPDATE runs as the signed-in user; RLS is the real gate. A refused UPDATE under RLS matches zero rows and is not an error, so the action selects the updated row and treats an empty result as "not saved".
- **Audit** (`/audit`): the latest 50 rows, with who (role and short actor id; admins cannot read `auth.users`, so no emails), table, action, row key and a field-by-field before and after diff (`src/lib/audit.ts`; `updated_at` and `updated_by` ignored; `predictor_weights` split per key).
- **Profiles** (`/profiles`): read-only list. PAN and mobile render only if they match the masked shapes of the DB CHECKs (`src/lib/masked.ts`); anything else becomes a placeholder and is never echoed.
- Nav and sign-out.

## Tests

- Unit (Vitest, `apps/admin`): 50 tests. Validation incl. boundaries 4/5/50/51 for every ranged field, empty and non-integer text (`Number('')` is 0, so text is checked first), the weights, the step permutation, the due-days list; `rawFromRow` round trip; audit diff; mask guard incl. a full PAN; the `saveRules` server action with mocked session and database (signed out, non-admin, 51, success, RLS zero rows, database error).
- E2E (Playwright, 8 including the existing smoke test): redirect when signed out, wrong password, sign in and out, an admin edit then its audit row (`threshold_pct: 30 -> 20`), a 51% threshold rejected with nothing saved, a non-admin cannot edit or see the audit log, profiles list never renders the unmasked PAN or mobile in the fake's deliberately leaky row. They run against `e2e/fake-supabase.mjs` (GoTrue password grant and `/user`, PostgREST `coach_rules` GET and PATCH, `audit_log` GET, `sample_profiles` GET), started by Playwright's `webServer`. It mimics RLS (a non-admin PATCH answers 200 with `[]`) and the CHECK constraints (400, code 23514), and appends an audit row on a changing PATCH. Next is built and started in production mode with the fake's URL in the build environment (`NEXT_PUBLIC_*` is inlined at build). No test switch exists in product code.
- The e2e `webServer` entries use `reuseExistingServer: false` and the specs run one at a time (`workers: 1`), because the fake keeps its state in memory and a reused dev server would have the wrong environment.

## Rulings and deferred items (each with its cost if wrong)

- **Sample profile create and edit: deferred.** `/profiles` is read-only; the PRD lists profile CRUD in the admin tests. Cost: about half a day (a JSON editor for `report` plus the `valid_sample_report` rules mirrored in a validator).
- **Users list: deferred.** The `admin_user_overview` view exists; the page does not. Cost: about 2 hours.
- **Card catalog and subscription presets: deferred.** They feed the next tier only and have no tables yet.
- **"Reset demo data" button and the daily reset: deferred.** It needs a service-role action or an RPC that does not exist (`reset_demo_data()` is mentioned in the migration but is not callable from this app). Cost: about 2 hours once the RPC is callable by admins. It matters only if judges get admin credentials.
- **No token refresh.** The one-hour access token is not refreshed; after it expires the admin signs in again. Cost: a minor annoyance during a long demo. A refresh in `proxy.ts` is about 1 hour of work.
- **No server-side revocation on sign-out.** Sign-out deletes the cookie; the token itself stays valid until it expires. Low impact for a single-admin tool.
- **Excellent line vs threshold:** the database has no `excellent_pct < threshold_pct` rule, so the form adds none. An admin can set an excellent line above the threshold. Cost: odd plan wording; the PRD and the migration are the place to decide.
- **Form fields reset to saved values** on a server-side rejection (React resets the form after an action). The browser check normally prevents that path.

## Owner steps

1. Fill `apps/admin/.env.local` from `.env.example`: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (anon key only).
2. Create an admin user in the dashboard (Authentication, Users, Add user, auto-confirm), then in the SQL editor: `update auth.users set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) || '{"role":"admin"}' where email = '<email>';`
3. `pnpm --filter @credit-coach/admin dev`, sign in at `/login`, change the threshold, and check `/audit`.
4. Apply the migrations first (`supabase db push`) if the hosted project does not have `coach_rules`, `audit_log` and the RLS yet.
