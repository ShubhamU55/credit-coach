1. **CRITICAL constraint for W2-1 and all future workflow authors**: passing FINDING_SCHEMA (or any schema with `allOf`/`oneOf`/`anyOf` at its OWN root) directly as `agent()`'s top-level `schema` option fails outright with a 400 API error ("input_schema does not support oneOf, allOf, or anyOf at the top level") — the agent never even runs. Confirmed twice (low and high severity attempts), both hard API errors, not a validation retry.
2. **Mitigation confirmed safe**: nesting FINDING_SCHEMA one level deep under a wrapper object property works fine — the `allOf` is no longer at the schema ROOT. This is structurally the same shape `envelopeSchema()` already uses for findings. **No design change needed for W2-1's actual planned calls** — but this is now a documented hard constraint for any future ticket.
3. A flattened copy of FINDING_SCHEMA with the `allOf` stripped also ran clean, confirming `type: ['integer','null']`, `maxLength`/enums/`agentType` all resolve correctly outside the `allOf`-at-root restriction.
4. Frozen contracts objects pass through untouched (`Object.isFrozen(FINDING_SCHEMA)` stayed true before and after every call), confirming W0-6's `deepFreeze` choice is compatible.
5. `agentType` resolution confirms W0-6/W1-1's custom agent types are reachable from a Workflow script.

Ruling: **binding constraint for every future workflow script (not just W2-1)**: never pass a contracts-block schema with a root-level `allOf`/`oneOf`/`anyOf` directly as `agent()`'s `schema`; always nest it under a wrapper object or array property, exactly as `envelopeSchema()` already does. Documented in a comment near FINDING_SCHEMA's definition in `contracts.mjs`. — If wrong: a future ticket's ad hoc single-finding `agent()` call hits a silent-looking 400 that isn't obviously about the schema shape.
