# PD-17 link: mobile app to the Supabase backend (2026-10-30)

Branch `feat/pd-17-app-backend`, worked by hand, test-first. Scope: `apps/mobile/**` only.

## What changed

- `src/backend/`: config (https-only env read), one lazy supabase-js client (in-memory session,
  `persistSession: false`, `autoRefreshToken: true`), background `startBackend` (anonymous sign-in then
  the single `coach_rules` row, 3 s per step, never throws), strict row parser mirroring the DB CHECK
  ranges, `BackendBootstrap` (renders nothing, mounted in `_layout.tsx`).
- `DemoRepository.applyRules`: replaces the rules, no-op and no notification when unchanged,
  `reset()` keeps them. Home, Plan and Score recompute through the existing `useRules` hooks.
- `explain/client.ts`: `getAccessToken` getter read at call time; `configFromExpoEnv` wires the
  in-memory anonymous token in, so a deployed function can return source `ai`. Grounding check and
  template fallback untouched.
- Dependencies (JS only, no native module, `android/` unchanged): `@supabase/supabase-js`,
  `react-native-url-polyfill`.

## Findings

- supabase-js sets `url.protocol`; React Native 0.88's built-in `URL` has no setter, so `createClient`
  throws on device without a spec URL class. A test with RN's own URL class reproduced it (RED), the
  polyfill (loaded lazily, only when a backend config exists) fixes it (GREEN).
- `useExplanation` is not called by any screen: the Plan screen renders `AIExplanation aiWritten={false}`
  with the engine template. The AI wording therefore cannot show until a screen uses the hook. Not done
  here (screens are out of scope to avoid a conflict with `feat/pd-17-polish`).
- Home and Plan build engine rules from `DEFAULT_COACH_RULES`, so `pay_by_buffer_days` and
  `planner_step_order` are validated but not applied. Only threshold, excellent, reporting basis and the
  guard line take effect.

## Mark as paid sheet insets (3-button navigation)

- Symptom: on a moto g73 (Android 14, targetSdk 36, edge-to-edge) in 3-button mode the tap on `mark-paid-confirm` hit the system Back button; gesture mode passed.
- Mechanism (from code, not measured): the formSheet route is drawn edge-to-edge and `SheetFrame` padded the bottom by a fixed 28dp only, so the Confirm button sat under the navigation bar. A gesture bar is small enough that the fixed padding cleared it.
- Fix: `SheetFrame` adds the bottom safe-area inset to its bottom padding and wraps the frame in a `ScrollView` (`mark-paid-scroll`). The inset is read from `SafeAreaInsetsContext` (null means 0), since `useSafeAreaInsets` throws without a provider. All testIDs are unchanged.
- Tests: `MarkPaidSheet.insets.test.tsx` (6): inset 48 pads form, Done and invalid by 28+48; inset 0 and no provider keep 28; the frame scrolls. Mobile Jest 978 pass, tsc clean, `pnpm verify` green.
- Could not verify: that a non-zero bottom inset is actually delivered inside the native formSheet on Android (expo-router wraps screens in `SafeAreaProviderCompat`, so it should be), and that the sheet's native height does not itself clip the content at the 0.6 detent. Needs the device run.

## Explain function flakiness: timeouts and auth diagnostics

- Evidence (live hosted project): repeated identical calls with a valid anonymous session alternated between 200 template, 503 `auth_unavailable` and 400/200. The Supabase Auth user lookup timed out intermittently; the model call may also have been timing out (cause not confirmed from logs).
- Numbers: `AUTH_TIMEOUT_MS` 600 -> 1500, `MODEL_TIMEOUT_MS` 2000 -> 2500, `EXPLAIN_TIMEOUT_MS` (app) 3000 -> 5000. Margins kept: model <= client - 750 (2500 <= 4250), auth + model <= client - 250 (4000 <= 4750). The relationship tests in `limits.test.ts` are unchanged; two pins were updated or added.
- Diagnostics: an auth failure now logs one line `explain auth unavailable timeout|http_<status>|network|no_config`, no token, header or body (tests assert this). Security logic untouched: the session is still confirmed with Supabase Auth, verify_jwt stays.
- Tests: slow-but-inside-budget lookup (1200 ms, fake timers) succeeds; one over 1500 ms gives `unavailable`.
- Other hard-coded numbers: `BACKEND_TIMEOUT_MS = 3000` in `apps/mobile/src/backend/start.ts` is a different call and was left alone.
- Not verified: live behaviour. The owner must redeploy and re-probe.
- Live logs showed every authenticated call logging `explain fallback http_400` with the reply body discarded. The reason now reads `http_<status>_<error.type>` (for example `http_400_invalid_request_error`). Only Anthropic's `error.type`, validated by `/^[a-z_]{3,40}$/`, is read; the message, request, key and prompt are never logged. A non-JSON or odd body keeps the plain `http_<status>`. Tests: `anthropic.errors.test.ts`.

## Gemini as the model provider for `explain` (owner call, 2026-10-30)

Ruling: the owner supplied a Gemini API key after the Anthropic key stayed unusable, and asked for it to replace Anthropic for the demo. `supabase/functions/explain` now calls Gemini (`gemini-2.5-flash`, override with the secret `GEMINI_MODEL`) when the secret `GEMINI_API_KEY` is set, and Anthropic otherwise. Only the provider call changed: the system prompt, the grounding check (`isAcceptableAiText`), the length and control-character checks, the template fallback and the app are untouched, so the LLM still only words numbers the engine already computed (CLAUDE.md rule 2).

- Rule 6 names the Anthropic key as the one model secret. The Gemini key is also only a Supabase Edge Function secret, never in the repo or the app, and goes in the `x-goog-api-key` header (never the URL). `CLAUDE.md` was not edited; this ruling records the deviation.
- Data sent to the provider: card names (already screened against PAN shapes), amounts, dates and percentages from the engine payload. No name, phone, email or PAN. On Gemini's free tier Google may use prompts to improve its products; that is acceptable for sample-profile demo data, and the free tier should not be used for real users' plans.
- Cost if wrong: the model id `gemini-2.5-flash` was not checked against the live API from this session (no key access). If it is retired or misspelled the function logs `explain fallback http_404_not_found` and answers with the template; set `GEMINI_MODEL` to fix it without a code change.
- Tests: `gemini.test.ts` (client: success, header, URL, error codes, truncation, refusal, timeout, network) and `handler.gemini.test.ts` (provider choice, Gemini preferred, fallback reasons, grounding still enforced, key never logged). `pnpm --filter` supabase suite 358/358, typecheck and eslint clean.
- Not run: any live Gemini call.
